# FabSim3D — 웹 앱 (M3)

교육용 반도체 공정 시뮬레이터의 실제 빌드입니다. 프로토타입 단계에서 단일 HTML
파일로 흩어져 있던 코어를 모듈 하나로 합치고, 파이썬 참조 구현을 오라클로 삼는
테스트를 붙였습니다.

## 왜 이 폴더가 생겼는가

M1·M2는 이 저장소를 만든 PC에 Node가 없어서 브라우저 아티팩트(단일 HTML)로
진행했습니다. 그 제약이 두 가지를 강제했습니다 — ① `m1b-core.html`과
`m2-ops.html`이 코어를 통째로 중복하고, ② 작성한 JS를 로컬에서 한 번도 실행해
보지 못했습니다.

현재 PC에는 Node가 있어 두 제약이 모두 사라졌습니다. 코어는 이제 한 곳
(`src/core/`)에만 있고, 프로토타입은 **회귀 기준선**으로 남아 테스트가 매번
대조합니다.

## 시작하기

```bash
npm install
npm run dev        # 개발 서버 → http://localhost:5173
npm test           # 코어 테스트 75건 (약 40초)
npm run smoke      # 브라우저 스모크 (dev 서버가 떠 있어야 한다)
npm run build      # 프로덕션 빌드
```

`npm run dev` 로 열면 트렌치 증착 예제가 바로 돌아 있습니다. 좌측 노드 에디터에서
파라미터를 만지면 **Run 버튼 없이** 고친 지점부터 다시 계산됩니다.

## 구조

```
src/core/          시뮬레이션 코어 — 프레임워크 무관한 순수 TypeScript
  data/              재질·공정 라이브러리 (JSON, 사용자 편집 대상)
  library.ts         JSON → 숫자 ID로 색인되는 조회표
  materials.ts       라이브러리에서 파생된 짧은 이름표 (SI, OX, …)
  grid.ts            Sim 컨텍스트와 스크래치 버퍼
  edt.ts             P1a 정확한 EDT + feature transform
  fmm.ts             P1b Fast Marching
  connectivity.ts    P2 연결성 + union-find 봉인·돌파
  visibility.ts      하늘 가시성 (스텝 커버리지)
  phi.ts             부호거리장, 지연 재거리화
  measure.ts         컬럼 꼭대기·보이드·재질 수 등 읽기 전용 측정
  masks.ts           마스크 생성
  ops/               공정 연산자 12종
  sequences/         표준·적대적 시퀀스 (화면과 테스트가 공유)
  project/           프로젝트 = JSON 하나 · 노드 카탈로그 · 그래프 · 예제 레시피
  runner/            실행기 (지연 평가 · 서명 캐시 · 취소) 와 RLE 스냅샷
  render/            단면 RGBA · 표면 메시 · 도핑 프로파일 (순수 함수)
  education/         진단(무엇이 잘못됐나)과 측정(얼마인가)
  __tests__/         아래 참조
src/worker/        시뮬레이션 Worker와 프로토콜
src/ui/            React 화면
scripts/smoke.mjs  브라우저 스모크 (Playwright)
```

시뮬레이션 코어에는 React도 Three.js도 들어 있지 않습니다. UI가 그 위에 얹히고,
Worker도 이 모듈만 import 합니다.

## 테스트가 무엇을 지키는가

| 파일 | 지키는 것 |
|---|---|
| `parity.test.ts` | 이식이 프로토타입과 **비트까지 같은가**. 재질·φ·도핑을 단계마다 해시로 대조하고, EDT 호출 횟수까지 본다. 코어를 리팩터링할 때의 안전망. |
| `primitives.test.ts` | 원시연산이 **애초에 맞는가**. EDT는 브루트포스와, FMM은 평면 소스에서 EDT와, union-find 봉인은 훑기 방식과 대조한다. |
| `golden.test.ts` | 파이썬 참조가 검증한 **물리 주장**을 TS가 재현하는가. Deal-Grove 54건은 자릿수까지, 나머지는 관계로 검사한다. |
| `sequence.test.ts` | 14단계 단언이 전부 통과하는가, 결정적인가, 지연 재거리화가 살아 있는가. |
| `library.test.ts` | 라이브러리가 제대로 해석·검증되는가, 그리고 **연산자를 안 고치고** 다른 재질로 동작하는가. |
| `project.test.ts` | 프로젝트 JSON이 왕복하는가, 실행기의 지연 평가·캐시·취소가 도는가, 그리고 **예제 레시피가 광고한 것을 실제로 가르치는가**. |
| `education.test.ts` | 진단이 문제를 잡아내는가, 그리고 **문제가 없을 때 조용한가**. 잘못된 경고는 진짜 경고를 묻는다. |
| `render.test.ts` | 단면 색·절단면·변경분 하이라이트·표면 완화. |

`parity`와 `primitives`의 역할이 다릅니다. 프로토타입이 틀렸다면 parity는 통과하고
primitives가 깨집니다.


파이썬 참조 구현(`web/reference/`)이 정본입니다. 새 연산자는 거기 먼저 넣어

## 재질과 공정은 데이터다

`src/core/data/materials.json` 과 `processes.json` 이 유일한 출처입니다. 연산자는
재질을 이름이 아니라 **속성**으로 판정합니다 — "산화막인가"가 아니라 "확산을
막는가", "PR인가"가 아니라 "노광되는가".

```
mat[i] === SI              →  oxidizesTo[mat[i]] >= 0
m === OX || m === NIT      →  diffusionFactor[m]
m === PR                   →  exposure[m] === EXP_RESIST
```

그래서 폴리실리콘 산화나 사용자가 편집한 장벽 계수가 연산자 코드를 건드리지 않고
동작합니다(`library.test.ts`가 그 둘을 실제로 확인합니다). 숫자 재질 ID는 JSON의
배열 순서이고, 0~7은 프로토타입 호환을 위해 고정입니다.

Unity 원본의 `EtchantConfig`/`CmpRateConfig`에서는 **이름과 구조만** 가져왔습니다 —
그쪽 선택비는 전부 1.0인 자리표시자였습니다.

## 교육 계층

시뮬레이터는 보이드가 갇힌 것도, 정지층이 뚫린 것도 이미 알고 있다. 문제는 학생이
화면만 보고는 **그게 문제라는 걸 모른다**는 것이다. 진단 패널이 그걸 말로 짚는다.

- **진단**: 아무 일도 안 한 단계, 봉인 보이드 발생·재개방, 정지층 뚫림, 레지스트
  소모(하드마스크 유무로 갈림), 실측 스텝 커버리지, 단차 위 노광, 정렬 오차,
  도즈 보존, 정지층 없는 CMP. 각 항목은 세어 본 값과 **고칠 노브 하나**를 같이 준다.
- **측정**: 프로브(컬럼 층 두께), 보이드 덩어리 통계, 변경분 하이라이트,
  재질 두께, 사이드월 각, 접합 깊이.
- **내보내기**: 단면 PNG, 단계표 CSV(진단 포함).

진단이 싼 이유는 프레임을 만들 때 통계를 한 번 재 두기 때문이다 — 패널을 열
때마다 92만 격자를 다시 훑지 않는다.

## 화면

단면 뷰가 주인공이고 3D는 보조입니다. 좌측이 노드 에디터, 우측이 3D·도핑
프로파일·속성 패널, 아래가 타임라인입니다.

- **Run 버튼이 없습니다.** 파라미터를 고치면 고친 지점부터 자동으로 다시 돕니다.
  성립하는 이유는 세 가지입니다 — 편집 디바운스, 보고 있는 단계까지만 계산하는
  지연 평가, 그리고 겹친 계산의 취소.
- 실행기는 (부모 결과, 노드 종류, 파라미터, 마스크)의 해시를 서명으로 써서
  **뒤쪽 노드를 고치면 앞쪽을 재사용**합니다. 분기끼리 공통 앞부분을 공유하는 것도
  같은 장치입니다.
- 스냅샷은 재질을 RLE로 압축하고, 도핑은 바뀐 단계에서만 새로 잡습니다.
  φ는 재개 지점에만, 그마저도 **꼭 필요한 단계에만** 둡니다 — φ를 더럽힌 채 끝난
  단계는 다음 증착이 어차피 다시 만들기 때문입니다.
- **마스크 디자이너**는 브러시가 아니라 사각형·다각형·스냅입니다. 실제 레티클이
  직선 도형이고, 손으로 칠하면 정렬 오차 실습이 무의미해지기 때문입니다.
- **재질·공정 표**를 화면에서 고칠 수 있고, 고친 표는 프로젝트에 함께 저장됩니다.
- 작업은 IndexedDB에 자동 저장돼 탭을 닫았다 열어도 하던 자리로 돌아옵니다.

## 알려진 특성

- **FMM은 평면 소스에서 정확하고 점 소스에서 대각선을 과대평가합니다**
  (24³ 격자에서 최대 22.5%, 평균 8.3%). 실제 사용은 전부 면 소스라 문제가 되지
  않습니다. 중요한 것은 **결코 과소평가하지 않는다**는 점입니다 — 전선이
  기하학적으로 가능한 것보다 일찍 도착하면 없는 재질까지 깎입니다.
- **격자 정렬 동점**: 거리가 정확히 정수인 셀은 부동소수점 누적 방향에 따라
  임계값 판정이 뒤집힙니다. 반 복셀 관례로 회피합니다.
- 성능(브라우저 실측): 150만 격자 0.71s/단계, 600만 2.15s/단계. 기본 격자는
  약 150만이고 600만은 고해상도 프리셋입니다.

## 3D 표면을 마칭큐브로 뽑지 않은 이유

두 가지입니다. ①스냅샷에서 φ를 뺀 결정 때문에 φ를 다시 만들려면 뷰마다 EDT
두 번이 듭니다. ②마칭큐브는 solid/empty 껍데기 하나만 주므로 **재질 경계가
사라집니다** — 어느 층이 어디까지인지가 이 도구의 핵심인데 그걸 잃습니다.

대신 추출한 면의 꼭짓점을 이웃 평균 쪽으로 당깁니다(표면 완화 슬라이더).
계단이 부드러워지면서 재질별 색은 그대로 남습니다.

## 테스트가 어디까지 보는가

```bash
npm test                          # 코어 117건
npm run dev  &&  npm run smoke    # 브라우저 스모크 11단계
npm run build && npm run serve:dist   # 빌드 결과를 직접 확인
node scripts/serve-dist.mjs dist 5200 FabSim   # 하위 경로에 올린 것처럼
```

마지막 줄이 중요합니다. Worker가 상대 경로로 로드되기 때문에 **하위 경로 배포는
개발 서버에서 절대 안 보이는 방식으로 깨질 수 있습니다.** CI가 매번 그 형태로
확인합니다.

`sandbox.test.ts`는 무작위 공정 순서를 만들어 두들깁니다 — 기판 없이 식각하고,
PR 없이 현상하고, 파라미터를 양 끝으로 밀어 봅니다. 목표 문서가 "모든 연산자가
모든 입력에서 유효한 결과를 내야 한다"고 못박았기 때문입니다. 이 테스트에는
**퍼즈가 실제로 어려운 경로에 닿는지 세는 검사**도 들어 있습니다. 처음 만든
퍼즈는 240단계를 돌면서 식각·산화·현상이 한 번도 동작하지 않았고 보이드도
하나도 안 만들었습니다 — 통과했지만 아무것도 확인하지 않은 셈이었습니다.

## 배포

`main`에 푸시하면 [GitHub Actions](../../.github/workflows/deploy.yml)가 타입 검사 →
코어 테스트 → 파이썬 참조 → 골든 값 대조 → 빌드 → 브라우저 스모크를 거친 뒤
GitHub Pages에 올립니다. **테스트가 깨지면 배포하지 않습니다** — 교실에서 쓰는
링크가 깨진 채로 올라가면 수업이 멈춥니다.

처음 한 번은 저장소 설정이 필요합니다: **Settings → Pages → Source를
"GitHub Actions"로** 바꾸면 됩니다.

손으로 올릴 때는 `npm run build` 후 `dist/`를 그대로 정적 호스팅하면 됩니다.
백엔드가 없고 모든 계산이 브라우저에서 일어나므로 링크 하나로 배포됩니다.
